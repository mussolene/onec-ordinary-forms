# Целевое состояние репозитория

Цель проекта: простая утилита для чтения, редактирования и сборки обычной формы как объектной модели с именованным XML 2.1 и отдельным `Module.bsl`. Словарь XML проекта вдохновлён читаемостью управляемых форм, но не совместим с форматом их выгрузки. Утилита не считается универсальной, пока фактическое покрытие бинарного кодека не подтверждено.

## Единственный продуктовый путь

```text
Form.bin -> OrdinaryForm -> Form.xml + Form/Module.bsl
Form.xml + Form/Module.bsl -> OrdinaryForm -> Form.bin
```

`OrdinaryForm` владеет объектами, идентификаторами, свойствами, значениями, событиями, элементами и модулем. `Form.bin` является форматом хранения. Если значение ещё нельзя собрать, добавьте именованное свойство или тип и его кодек в обычный путь, после чего зафиксируйте проверку. Не публикуйте низкоуровневые записи, сырые потоки или сохранённый бинарный профиль в XML.

## Порядок расширения

Расширяйте контролы и свойства небольшими проверяемыми шагами:

1. Найдите обычный платформенный тип, его XML-имя, свойства, события и типизированные значения в метамодели (`src/model/metamodel.cpp`) и XML-адаптере (`src/source/form_xml.cpp`).
2. Проверьте, что XML 2.1 читает, сериализует и повторно читает новое именованное представление; добавьте XML-тесты в существующий `tests/form_xml_test.cpp`.
3. Отдельно исследуйте бинарное представление и добавьте кодек с дескрипторами для `OrdinaryForm` и слоя хранения. Не считать наличие типа в XSD управляемых форм доказательством поддержки записи обычной формы.
4. Добавьте тесты сериализации `Form.bin`, затем проверьте результат строгой выгрузкой Designer при доступности платформы. Если платформа недоступна, запишите ограничение, не объявляя покрытие завершённым.
5. Отразите достигнутое покрытие и оставшиеся случаи в проверках и документации; сохраняйте XML именованной объектной моделью.

Целевой охват: 25 типов из текущего каталога без внешнего `ActiveXControl`. Саму форму, страницы, колонки, команды, реквизиты, события и привязки учитывать дополнительно. ActiveX исключен из требований по решению пользователя от 2026-09-24.

Тест `test_all_control_variants` по-прежнему покрывает цикл XML-разбора и сериализации для 26 типов каталога, включая ActiveX. Наличие этого XML-типа не означает обязательства реализовать его бинарный кодек. Каждый из 25 целевых типов требует отдельного бинарного свидетельства перед заявлением о поддержке сборки.

До добавления CheckBox для Button, LabelDecoration и InputField были подтверждены четыре синтетических состава на 3, 5, 5 и 6 элементов, включая обратные ID, две надписи и общий реквизит двух полей. Вложенные элементы, остальные свойства и типы значений этим не покрыты. Все 11 CTest той итерации прошли. Сборки без исходного Form.bin проходили строгую выгрузку Designer 8.5.1.1343; обратное чтение сохранило именованные значения и модуль.

Дополнительно проверен состав из шести элементов четырех типов: три CheckBox,
LabelDecoration, InputField и Button. Исходный Form.bin отсутствовал перед
сборкой. После строгой выгрузки Designer публичный XML совпал побайтово,
модуль сохранился с учетом перевода окончаний строк. Отдельная правка Caption
и повторная сборка изменили ровно одну строку XML. Это доказательство для
перечисленных свойств, а не всех настроек флажка: ThreeState, его события,
вариант без DataPath и другие типы данных пока не поддержаны.

Итоговая проверка этого изменения: `make test` на macOS arm64 и свежая
Release-сборка на Debian 12 amd64 прошли по 11/11 тестов. Обе утилиты
выдали побайтово одинаковые Form.bin, Form.xml и Module.bsl для смешанной
формы. Свежий Designer также показал флажок с булевым реквизитом и заданными
свойствами. Windows в этой итерации не проверена.
Свидетельство: `ev_1c10b80d054d41119f75d86968712298`.

Статусы этой таблицы: `NOT_SUPPORTED` означает отсутствие подтвержденного бинарного цикла, `PARTIAL` означает проверенный цикл только для перечисленных свойств и составов. `UNKNOWN` относится к неустановленной семантике конкретного значения. Наличие имени, GUID или типа XSD не повышает статус. Полная поддержка типа требует сохранения всех заявленных свойств, событий и связей, а не только успешной загрузки формы.

## Ближайшие этапы

Состояние на 2026-10-03: первый этап выполнен частично. Подтверждены несколько
Button, порядок Button, LabelDecoration, InputField и один InputField без
этих соседей с одним строковым реквизитом и DataPath. Также подтверждены два
InputField с двумя строковыми реквизитами и отдельными DataPath.
Текущая итерация расширила смешанные составы до четырех типов, добавила
HorizontalAlign Auto/Left у надписи и CheckBox с общими или отдельными
булевыми реквизитами. Сохранение порядка при обратных ID подтверждено.
У InputField редактируются ID, имя, Position,
Enabled, ReadOnly и строковые квалификаторы реквизита; независимая сборка XML и строгая
выгрузка Designer сохраняют значения. Вложенные составы элементов,
остальные типы реквизитов и обработчики InputField еще не проверены.
Текущие свидетельства и границы приведены в `docs/research-map.md`.

1. Одна реальная форма: корневая идентичность, несколько Button, LabelDecoration, InputField, реквизиты и обработчики. Критерий: изменение именованного XML, сборка без исходного Form.bin и строгая повторная выгрузка Designer с проверкой измененных значений.
2. Panel/Page, вложенность и привязки размеров/реквизитов; затем CommandBar и Table на реальных примерах. Каждый новый вариант получает тест чтения, изменения и записи.
3. Остальные стандартные элементы, картинки и сложные документы. Покрытие учитывать по типам и свойствам, а не по числу записей в XSD. Внешний ActiveX в этот этап и критерии готовности не входит.
4. Только после подтверждения согласованного набора форм завершать установку, упаковку и выпуск. Общая цель остается поддержкой всех 25 целевых типов и связанных объектов формы, первый этап служит проверкой механизма и не заменяет ее.
