# Разработка

## Рабочий цикл

1. Настройте и соберите продуктовый путь: `make build`.
2. Запустите продуктовые тесты: `make test`, затем CLI smoke: `make smoke`.
3. Подготовьте каталог исходников: `Form.xml` и обязательный соседний `Form/Module.bsl`. Для пустого модуля создайте пустой файл.
4. Отредактируйте именованные элементы и свойства в `Form.xml`, код в `Module.bsl`.
5. Соберите `Form.bin` командой `build/sidecars/onec-form-native/oof build <Form.xml> <Form.bin>`.
6. При наличии локальной платформы проверьте EPF/ERF через `tools/platform_validate_epf.sh <processor.epf>`.

Путь `dump` создаёт XML и каталог модуля, путь `build` читает оба источника. `oof --help` показывает CLI-контракт. Правки выполняются непосредственно в XML и BSL; отдельных команд редактирования и сравнения нет.

## Что подтверждают проверки

`make test` запускает тесты объектной модели, XML-адаптера и бинарных слоёв. В частности, `test_all_control_variants` проверяет чтение и запись XML для 26 объявленных типов контролов. Это утверждение только про XML-модель и сериализацию XML. Оно не доказывает поддержку соответствующего бинарного кодека `Form.bin` для каждого контрола или свойства.

`make smoke` проверяет CLI, включая команду версии и интеграционный сценарий. Ни XML-тест, ни smoke не заменяют проверку потока самой платформой. Успешная сборка `Form.bin` удостоверяет лишь то, что текущий writer принял источник. Строгая Designer-выгрузка проверяет, что платформа смогла прочитать поток. Метаданные от `ibcmd config load/check` отдельно не подтверждают открытие обычной формы.

Проверка EPF требует локальной установки/контейнера платформы и доступной лицензии:

```sh
export OOF_PLATFORM_CONTAINER=<имя-локального-контейнера>
tools/platform_validate_epf.sh <локальный-путь-к-processor.epf>
```

Не добавляйте в Git частные EPF/ERF, выгрузки конфигураций, лицензии и локальные логи. Для экспериментов используйте игнорируемые `work/` или `scan-output/`.

## Пилот свойств Button

`tools/verify_button_property_pilot.py <manifest.tsv> [run-dir]` последовательно
проверяет четыре заранее подготовленных варианта EPF: `base`, `base-repeat`,
`caption` и `enabled`. Соберите продуктовый CLI командой `make build` и задайте
`OOF_PLATFORM_CONTAINER` для уже запущенного контейнера платформы. Скрипт
копирует исходные EPF в отдельные каталоги запуска, вызывает строгую выгрузку
Designer для каждой копии и читает единственный свежий `Form.bin` из ее каталога
выгрузки командой `oof dump`. Отчет и копии EPF остаются в новом каталоге
`scan-output/`.

Подготовьте локальный TSV манифест вне Git, например в `work/button-pilot.tsv`.
Пути EPF могут быть абсолютными или относительными к каталогу манифеста. Внесите
одинаковое имя Button во все строки; `base-repeat` повторяет значения `base`,
`caption` меняет только подпись, а `enabled` меняет только логическое значение.
Укажите источник подготовки как `platform-ui`, `oof-writer` или `unknown`.
Метка происхождения задается вручную и не подтверждается скриптом.

```tsv
role	epf	button_name	caption	enabled	provenance
base	base.epf	PilotButton	Исходная подпись	true	platform-ui
base-repeat	base-repeat.epf	PilotButton	Исходная подпись	true	platform-ui
caption	caption.epf	PilotButton	Измененная подпись	true	platform-ui
enabled	enabled.epf	PilotButton	Исходная подпись	false	platform-ui
```

Запустите проверку:

```sh
tools/verify_button_property_pilot.py work/button-pilot.tsv
```

`verification_status` описывает локальные проверки скрипта: `PASS` означает,
что строгая выгрузка Designer и чтение ожидаемых именованных значений прошли
для всех четырех вариантов; `FAIL` означает ошибку; `PARTIAL` означает, что
проверки не удалось завершить полностью. Коды завершения: `0` для `PASS`, `1`
для `FAIL`, `2` для неверных аргументов или входных данных, `3` для `PARTIAL`.
Поле `overall` равно `FAIL`, если проверка не прошла; после успешных проверок оно
остается `PARTIAL`, пока происхождение вариантов и независимое изменение через
интерфейс платформы не подтверждены отдельно. Скрипт читает значения собственным
`oof` и сам по себе не доказывает соответствие декодирования модели свойств
платформы. Для этого нужны сохранение через Designer, закрытие Designer,
повторное открытие сохраненной EPF и проверка значений в интерфейсе.

Для просмотра позиционных различий между свежими потоками формы используйте
исследовательский сравниватель. Замените имя каталога на каталог отчета текущего
запуска:

```sh
run=scan-output/button-property-pilot-actual-diag-20260924T125045Z-23059
c++ -std=c++20 -I sidecars/onec-form-native/include \
  tools/compare_form_streams.cpp -o "$run/compare-form-streams"
"$run/compare-form-streams" \
  "$run/base/platform/dump/root/Forms/Форма/Ext/Form.bin" \
  "$run/base-repeat/platform/dump/root/Forms/Форма/Ext/Form.bin" \
  "$run/caption/platform/dump/root/Forms/Форма/Ext/Form.bin" \
  "$run/enabled/platform/dump/root/Forms/Форма/Ext/Form.bin"
```

Сравниватель разбирает только логический поток `form` внутри `Form.bin` и
показывает отличия дерева по позиционным путям. Он не сравнивает поток модуля,
не определяет смысл позиции и не классифицирует служебные изменения. Поэтому
позиционное отличие нельзя автоматически объявлять свойством формы. Исходные
EPF и их подготовка в интерфейсе платформы являются отдельными входными данными;
само сравнение не подтверждает происхождение вариантов. Полный автоматический
генератор вариантов и свойств пока не реализован. Вывод может содержать до 96
байт измененного значения, поэтому используйте только синтетические формы и
оставляйте отчеты в `scan-output/`.

## CI и выпуск

GitHub Actions запускает `make test` и `make smoke`. `make release-gate` сейчас намеренно заблокирован и завершается ошибкой: строгая проверка платформой и проверка набора форм ещё не выполняются этим gate. Успешные модульные тесты не означают полного покрытия бинарного формата. Не заявляйте готовность, пока поддержка кодека не подтверждена для конкретных значений и строгой проверкой платформы.
