# Разработка

## Ветка и границы задачи

Работайте в собственном worktree и ветке от актуальной интеграционной ветки
`matvienko/product-model-rebuild`. Одна ветка должна решать одну ограниченную
задачу и завершаться одним проверяемым pull request. Не вносите изменения
непосредственно в интеграционную ветку или `main`.

До правки запишите ожидаемые публичные типы, свойства и значения по умолчанию,
допустимые сочетания и случаи явного отказа. Используйте существующую модель,
метаданные и кодеки. Статус экспериментальной сцены или открытого pull request
не добавляет поддержку продукту: учитывайте только код, уже находящийся в
текущей интеграционной ветке.

## Исходники формы и CLI

Редактируемый продуктовый источник состоит из именованного `Form.xml`,
соседнего `Form/Module.bsl` и файлов ресурсов, например
`Form/Items/<ElementName>/Picture.gif`. Публичный XML объявляет
`ordinaryFormVersion="2.1"` и размещает элементы внутри `ChildItems`. Это
модель обычной формы, а не XML-формат управляемых форм. Ограничения свойств
смотрите в [матрице типов](repository-target-state.md#измеряемый-прогресс) и
[контракте OrdinaryForm](ordinary-form-target-contract.md#concept-registry).

CLI обрабатывает отдельную форму и не требует платформы 1С. Для сборки и
проверки используйте:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release
ctest --test-dir build --build-config Release --output-on-failure
make smoke
build/sidecars/onec-form-native/oof --help
```

`dump` создает именованный XML и соседний каталог модуля. `build` читает XML,
`Module.bsl` и ресурсы из соседнего пакета и записывает новый `Form.bin`; прежний
`Form.bin` для этой команды не нужен. Например:

```sh
build/sidecars/onec-form-native/oof dump input/Form.bin work/Form.xml
${EDITOR:-vi} work/Form.xml
${EDITOR:-vi} work/Form/Module.bsl
build/sidecars/onec-form-native/oof build work/Form.xml output/Form.bin
```

Обычная сборка CMake, CLI и его тесты не обращаются к платформе. Успешная
команда `build` подтверждает только, что модель и код записи приняли источник.

Матрица фиксирует свойства и недостающие варианты отдельно для каждого типа.
Не переносите этот общий процент на готовность продукта.

Для нового свойства используйте достаточную для его контракта последовательность:

1. Тесты модели и XML проверяют именованное значение, значение по умолчанию,
   каноническую запись и явный отказ на неподдержанный ввод.
2. Тесты потока проверяют чтение и запись `Form.bin` без исходного потока.
3. Синтетическая сцена из именованного XML проходит сборку CLI, строгую проверку
   Designer и, когда значение доступно при выполнении, холодную проверку
   возвращаемых свойствами значений и связей с отдельным отчетом.

Строгая проверка требует платформу и доступную лицензию. Для готового EPF или
ERF используйте:

```sh
export OOF_PLATFORM_CONTAINER=<имя-локального-контейнера>
tools/platform_validate_epf.sh <локальный-путь-к-processor.epf>
```

Для новой синтетической формы, исходный `Form.bin` которой создан CLI в дереве
источника вместе с метаданными, выполните строгую загрузку и холодную проверку:

```sh
OOF_PLATFORM_CONTAINER=<имя-локального-контейнера> \
  tools/platform_oracle_execute.sh \
  scan-output/<сцена>/source/root.xml \
  scan-output/<сцена>/check.bsl \
  scan-output/<сцена>/runs/cold
```

Проверка метаданных через `ibcmd config load/check` не заменяет открытие потока
формы Designer. Если среда или один из уровней доказательства недоступны,
фиксируйте точное ограничение как PARTIAL или UNKNOWN. Не закрывайте критерий
успешным несвязанным тестом и не заявляйте поддержку только по XSD, сборке CLI
или эксперименту.

Все опыты и локальные отчеты держите в игнорируемых `work/` или `scan-output/`.
Не добавляйте в Git частные EPF/ERF, выгрузки конфигураций, лицензии,
платформенные файлы и локальные логи.

## Pull request и выпуск

Перед pull request проверьте текущую интеграционную ветку и матрицу. Добавьте
только относящиеся к задаче исходники и доказательства, напишите описание по
фактическому поведению и укажите результаты проверок. В pull request должно
оставаться одно связное изменение; новая задача получает отдельную ветку и
отдельный pull request.

CI запускает `make test` и `make smoke`. `make release-gate` намеренно
заблокирован, пока строгая проверка платформой и проверка набора форм не входят
в механизм допуска. Не выпускайте продукт и не называйте его готовым до
достижения целевого контракта и успешной полной проверки. Частичная поддержка должна оставаться
явной в матрице, даже если все доступные тесты прошли.
