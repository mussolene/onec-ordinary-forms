# Карта завершения и платформенных референсов

<a id="implementation-map"></a>
## Единая карта реализации

Точка отсчета: код `ef5dd742f2a002797a1c8c15f396bd93860a5a48`,
платформа 8.5.1.1343 Linux. Статус `PARTIAL`.
[Замер и критерии приемки](repository-target-state.md) отделены от этой карты.

Решение: завершать семейства сохраняемых объектов в существующей именованной
модели. SO/DLL служат источником правил и независимым эталоном. Их не нужно
переносить в продукт или заново исследовать для уже известных Color, Font,
TypeDomain и других общих значений.

## Граница замены реализации

Целевая платформа чтения и сборки: 8.5.1.1343 Linux. Ее Load читает также
сохраненные ранее поколения компонентов. Ограничение платформы не означает
отказ от старых входов корпуса. Выходной writer использует поколения 8.5;
обратная совместимость результата с 8.2 сейчас не является критерием выпуска.
Существующий явный контракт версий SpreadsheetDocumentField сохраняется.

Разрешена полная замена неверного кодека внутри `storage`. Единица переноса
из SO состоит из всего жизненного цикла семейства:

1. Фабрика создает объект, владелец задает контекст и начальные значения.
2. Load выбирает грамматику по версии записи и читает явные значения.
3. Реестр объектов разрешает идентичности, ссылки и источники команд.
4. Модель различает сохраненное состояние, вычисляемое представление
   и автоматически созданные объекты.
5. Save записывает предусмотренные платформой объекты и значения.

Для меню это цепочка DesignedCommandInterface, DesignedCommand,
DesignedBandSource и DesignedButton. Сравнение записи с одним заново
закодированным образцом не заменяет эту цепочку. Независимые сохраняемые
значения нельзя выводить друг из друга только потому, что они совпадали
в синтетическом примере. Старый неполный алгоритм не остается резервным путем.

`OrdinaryFormDocument`, XML/XSD, модуль, ресурсы и общие кодеки значений
остаются существующими владельцами. Недостающее состояние получает
подтвержденное именованное понятие, а не поле с номером позиции потока.

`MetadataContext` является индексом типов и членов конфигурации для
разрешения имен и связей. Это не экземпляр native корня метаданных.
Настоящая конфигурация и данные нужны в базе нативной приемки зависимых форм.
Копирование всего runtime метаданных в продукт не требуется для этого
индекса и не заменяет мост из XML к новому native объекту.

Ресурсы XDTO/XSD используются как источник имен и контрактов значений.
В текущем наборе проверены хеши всех 81 извлеченных схем. Найденный в них
`Form` относится к управляемой форме; готовая универсальная XDTO-сериализация
обычной формы этим набором не подтверждена. Таблицы имен свойств и исполнителей
помогают установить семантику, но индекс строки ресурса нельзя считать
идентификатором сохраняемой команды. Для нее нужна связь регистрации,
идентификатора, владельца и Load/Save.

Проверенный общий механизм композиции: GanttChart и Dendrogram создают
настоящий Chart и делегируют ему `IPersistableObject::Load/Save`. Поэтому
их агрегат читает и пишет существующий кодек Chart, включая коллекции,
области, шрифты и другие именованные свойства. Отдельный шаблон вложенной
диаграммы удален из конструкторных записей; начальные значения задаются
типизированно перед общим Save. События и BackColor остаются у владельца.

Общий Picture сохраняет идентичность встроенного ресурса и координаты
прозрачности. ICO/DIB является обычным файлом картинки, без дополнительной
обертки платформы. Его отсутствие в нашем списке форматов объясняло 1477
первых отказов промежуточного замера; это не число новых полных форм.
У абсолютной Border пустой идентификатор семейства равнозначен стандартному
ControlsBorders, что подтверждено `V8Border::operator==` в core85.
Референсы этих правил и проверка схем: OACS
`ev_ada2911c94e44325a49de07bc6b74f7e`.

ControlCommandHandler сохраняет идентификатор команды и ее контекст
независимо: Load `0x2d5bf90`, Save `0x2d5bd90` в проверенном frame.so.
Поэтому зарегистрированные команды используют общую пару чтения/записи
явных Form/CommandBar и источников Form/AllSources/Control. Default имеет
отдельное представление; неподтвержденные варианты не превращаются в него.
Автоматическая команда формы с подписью Справка дает ID 300, представленный
именем Help. Нативный набор из 30 владельцев подтвердил сохранение ссылок,
редактирование Text и повторное открытие после самостоятельной сборки.
Вызов Help, остальные неизвестные ID и все варианты Default не доказаны.
Референсы и замер: OACS `ev_ee2d25a8b6474d12aafe06bb8bfef602`.

Прямое исполнение SO не является готовой заменой: tracked FormDocument
probe проверяет фабрику, создание интерфейсов и RTTI, но не строит форму
из XML и не устанавливает ее свойства. Новый host платформы не входит
в выбранный путь. Переносится проверенный алгоритм в самостоятельный кодек.
Независимая проверка 8.5.1.1343 уточнила границу: `frame.so`, `basicui.so`
и `dsgnfrm.so` экспортируют точки запуска `DllMain` и `SCOM_Main`, но не
самостоятельно вызываемые `CustomForm::Load/Save`. `core85.so` загружается
отдельно, а загрузка `frame.so` вне платформенного процесса аварийно
завершается во время инициализации. Перехват `Load/Save` работает внутри
Designer с созданным им контекстом; отдельному CLI пришлось бы создавать
контекст владельца, хранилище и объектную привязку всех именованных свойств.
Это результат ограниченного опыта, а не доказательство невозможности любого
моста, OACS `ev_e7532fcd41734fbb8051362000b9c91d`.
Основания границы и цепочки инициализации: OACS
`ev_8fe05e74060b45aead4bf33956b78735`; независимый нативный набор:
`ev_13cf5f4bd29d4bc28d89fc7ffaeb5bdc`. Последующая трасса замкнула источник
второй настройки: `ClientInterfaceTheme` приходит от окна владельца и не
вычисляется из `ClientInterfaceVariant` (`ev_65fd922518c0491da6d3c75eb3d3a89e`).
Отдельный `CommandControlKind` сохраняет выбор вида из источника либо явной
кнопки. Это подтверждено фабрикой визуальных элементов и RTTI, а не сходством
чисел со схемным перечислением (`ev_4007cfe02c5f40599c078d77d150fdb9`).

## Порядок работ

| Приоритет и семейство | Что отсутствует или ограничено | Владельцы | Условие завершения |
| --- | --- | --- | --- |
| 1. Коллекции Menu и команды источника | Дополнительные стандартные команды и виды визуальных элементов источника, неподтвержденные варианты автоматического размещения | `CommandBarButton`/`StandardMenuAction`, метамодель, `decode_button_menu`, writer меню, XML/XSD | Именованная модель сохраняет коллекцию, порядок, действия и изменения; независимые нативные примеры; прирост полных форм измерен |
| 2. Table и редакторы | Старые оболочки колонок, типы источников, идентичности стандартных полей, парные описания редакторов | `TablePayload`, `TableColumn`, metadata context, кодеки Table/вложенных контролов | Таблица собирается из XML с данными, типами, связями и редакторами; сравнение после изменения и повторного открытия |
| 3. Общие поколения и остатки записей | Арность, корень/владелец, расширения, отличия от канонического образца, составные значения | `probe_layout`, общие decoder/encoder в `form_stream.cpp`, `value_codec.cpp` | Поддержанная версия имеет полную пару чтения/записи; нет непредставленного значимого остатка |
| 4. Полный пакет и Commands | Непустая коллекция Commands пока не записывается; отдельное хранение такой коллекции у обычной формы не подтверждено справкой 8.5, остаются ограничения идентичностей и владения | `OrdinaryFormDocument`, метамодель, XML, `encode_document` | Подтвердить платформенный объект либо представить команды через действия CommandBar; схема сама по себе не доказывает поддержку |
| 5. Поколения входов | Reader должен покрывать старые записи, принимаемые целевой 8.5; независимый writer для 8.2 отложен | Версионные ветви Load в существующих кодеках, современные парные writer | Старый вход преобразуется в полную именованную модель; выход 8.5 сохраняет ее данные и поведение |
| 6. Полная приемка и выпуск | Корпус, сочетания форматов и владельцев, актуальный манифест выпуска | Существующий корпусный стенд, Designer, CTest, `release_gate.py` | Все условия полной приемки PASS; нет частичных и пропущенных целевых форм |

Это зависимости, а не шесть новых подсистем. Этапы 1-4 используют одни
дескрипторы, модель, XML и кодеки; не создают отдельный reader для каждой формы.
Точную очередность внутри этапов уточняет замер после завершенного семейства.
Работу по поколениям выполняют вместе с соответствующим семейством.
Поддержка reader без самостоятельного writer для целевой 8.5 не считается
завершением. Отложенный старый writer не блокирует эту приемку.

14 кодеков состояния выполнения идут отдельным ограниченным контрактом
[#49](https://github.com/mussolene/onec-ordinary-forms/issues/49). Они не
оправдывают потерю сохраненных данных и не должны задерживать замыкание
обычного XML/BIN пакета. ActiveX вне цели, [#50](https://github.com/mussolene/onec-ordinary-forms/issues/50).

## Ближайший замкнутый результат: Menu

Уже установлено на `DesignedBandSource::Load/Save`:

- AutoFill коллекции отличается от свойства `CommandBar.AutoFill`.
- Сохраняется намерение размещения автоматически созданных кнопок;
  отсутствие кнопок не доказывает, что значение можно очистить.
- Отдельно хранится включенное автоматическое членство, а не список исключений.
- Порядок кнопок, идентичность самой кнопки и цель подменю различаются.
- Вариант интерфейса, тема и вид визуального элемента команды независимы.
  Для них есть именованные свойства и самостоятельный writer.
- Команда источника требует именованного разрешения; произвольная пара
  UUID/число не должна попадать в публичный XML как скрытая сырая запись.

Существующий разбор: `scan-output/menu-collection-contract-20261112/contract.md`
и `group-identity-contract.md`. Сокращенные выводы первого документа
о членстве Load/Save требуют поправки: автоматические Action и Separator
не сохраняются отдельно, а регистрация источника подменю использует другой
реестр. Актуальное уточнение: `ev_72e3f6a492334d04bfa19196847ded8a`.
Данные применяются только к проверенной библиотеке.
Разбивка первых отказов: `ev_814c0a41803d454ca5c8d61afecedae8`.
Проба пустых коллекций не вызвала нужные Load/Save и не доказывает семантику
автоматического размещения. Этот опыт не повторять как положительную приемку.

Рабочий пакет:

1. Закрепить именованные понятия коллекции и команды источника в существующей
   модели, без индексного публичного формата.
2. Одновременно подключить декодирование, XML/XSD и самостоятельную запись.
3. В одном нативном наборе проверить минимум десять применимых контролов,
   пустые/непустые коллекции, разные источники, вложенность, размещение,
   локализацию и изменение команды. Сравнить поведение и сохраненные данные.
4. Прогнать полный корпус после замыкания семейства. Сообщить новые полные
   формы, переходы partial/reject и регрессии, а не число снятых первых guards.

Ведущий исполнитель владеет моделью и интеграцией. Один ограниченный
субагент может независимо проверить нативный набор или точный контракт
Load/Save. Несколько исполнителей одновременно не меняют `form_stream.cpp`.

Пути владельцев ниже относятся к `sidecars/onec-form-native`.

| --- | --- | --- |
| `core85.so`, `core82.dll` | Интерфейсы контекста, типы значений, CompositeID, ListInStream/ListOutStream | `model/metamodel.*`, `storage/value_codec.*` |
| `frame.so` | Настоящий CustomForm, фабрика, RTTI, IPersistableObject, корень и рекурсивные Load/Save | `model/ordinary_form.*`, `storage/form_stream.*` |
| `basicui.so` | Контроллеры и расширения формы, их события и сохраняемые настройки | Реестр расширений метамодели и кодеки формы |
| `dsgnfrm.so`, `dsgnfrm.dll` | Оболочка FormDocument и штатные операции Designer | Нативная приемка, не отдельная публичная модель |
| `mngui`, `mngbase`, `mngcore`, `frmcore` | Конкретные фабрики, источники и UI-объекты по цепочке владения | Дескрипторы источников, колонок, редакторов и связей |
| `enums.so`, справка, XDTO/XSD | Имена, перечисления, применимость, структура стандартных типов | Метамодель, palette, схема типов |

Наличие строки GUID или импорта не доказывает владение. Нужна цепочка:
регистрация -> фабрика -> объект/интерфейс -> Load/Save -> именованное понятие.
Общий GetPropVal/SetPropVal не раскрывает автоматически все сохраняемые
состояния, вложенные коллекции и отношения владения.

Инвентаризация Linux и Windows: `ev_9465e7269bab4356b25431b755ca656b`.
Референс 8.2.19.130 под Wine: `ev_b6d61188becb4d5bae37d662f684d8d0`.
Массовое скачивание всех 8.3 не требуется. Следующая версия нужна только
для конкретного различия, не объясненного имеющимися референсами.

## Проверка без повторных расследований

Для каждой итерации сначала воспроизводится конкретный разрыв на текущем
коде. Существующий общий кодек проверяется прежде нового исследования.
После изменения выполняются профильные тесты и один нативный набор.
Полный корпус запускается после завершения семейства, а не после каждого поля.

Для зависимых форм стенд содержит совместимые метаданные и необходимые
данные. После загрузки конфигурация применяется по F7; выгрузка выполняется
из этой базы. Пустая база скрипта строгой выгрузки не является подходящим
контекстом для произвольной прикладной формы.

Простое сохранение EPF может не загрузить поток формы. Проверяется настоящее
открытие, Load/Save и повторная строгая выгрузка. Изменяются и сравниваются
свойства, события, связи, порядок, типы реквизитов, модуль и ресурсы.
Сравнение не очищает непонятные различия ради PASS.

Нативное подтверждение 8.5 не доказывает работу в 8.2. Проверка 8.2 выполняется
в старой платформе, без приписывания ей CLI выгрузки исходников новой версии.
Различия ОС и поколений платформы также учитываются раздельно.

Короткие результаты и следующая задача записываются в OACS. Подробные
временные отчеты имеют владельца и сохраняются в игнорируемом каталоге.
История экспериментов не дописывается к нормативному контракту после каждой
пробы; туда попадает только принятое изменение поведения.
