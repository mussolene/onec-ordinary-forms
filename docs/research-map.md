# Research Map

This repository keeps research notes at the level of verified approach,
sanitized tool behavior, and public references. Do not commit private
processors, customer exports, full platform dumps, disassembly output, license
configuration, OACS state, or host-specific paths.

## Direction

The ordinary form model is built from three evidence sources:

- platform export/import behavior;
- public documentation and prior art for ordinary form controls;
- small sanitized observations from platform libraries.

Public articles and repositories are useful for vocabulary and comparison, but
the serializer should be treated as correct only after a platform round trip
confirms it.

## Delphi DFM и работа с Git, 2026-10-03

Delphi дает полезный образец текстового представления формы, но сходство
редакторов и наличие сетки не доказывают, что обычные формы 1С используют
DFM, VCL или ту же сериализацию.

У Delphi разделены преобразование формата и создание объектов:

```text
текстовый DFM <-> двоичный поток компонентов
двоичный поток -> TReader -> экземпляры компонентов и связи
```

`ObjectTextToBinary` преобразует текст в поток через `TWriter`; для получения
самого объекта документация отдельно указывает `ReadComponent`.
[Источник: ObjectTextToBinary](https://docwiki.embarcadero.com/Libraries/Athens/en/System.Classes.ObjectTextToBinary).
`TReader` создает компоненты по именам классов, присваивает опубликованные
свойства и разрешает ссылки между компонентами.
[Источник: TReader](https://docwiki.embarcadero.com/Libraries/Athens/en/System.Classes.TReader).
Обработчик события ищется по имени метода.
[Источник: TFindMethodEvent](https://docwiki.embarcadero.com/Libraries/Sydney/en/System.Classes.TFindMethodEvent).

Не все сохраненные данные обязаны быть обычными опубликованными свойствами.
Через `DefineProperty` и `DefineBinaryProperty` компонент объявляет
дополнительные именованные данные и собственные функции чтения/записи;
двоичное значение труднее редактировать текстом.
[Источник: DefineProperty](https://docwiki.embarcadero.com/Libraries/Florence/en/System.Classes.TReader.DefineProperty),
[Источник: DefineBinaryProperty](https://docwiki.embarcadero.com/Libraries/Athens/en/System.Classes.TReader.DefineBinaryProperty).
Следовательно, поиск общего корня и описания свойств полезен, но сам по себе
не гарантирует, что все сложные значения описываются одним универсальным XSD.

Embarcadero прямо рекомендует текстовые файлы форм для внешних инструментов
и систем контроля версий. Сетка и привязка к ней описаны отдельно как
средства размещения элементов, не как формат файла.
[Источник: Form Designer Options](https://docwiki.embarcadero.com/RADStudio/en/Form_Designer_Options).

Для этого проекта применимы следующие правила. Это инженерный вывод из
сравнения, а не утверждение о внутреннем формате 1С:

- Единственный исходник формы: именованный `Form.xml`, отдельный
  `Form/Module.bsl` и файлы картинок по существующему контракту.
- Общая модель владеет типами, свойствами, событиями и ссылками.
  Сериализатор восстанавливает поток из этой модели; наличие исходного
  `Form.bin` для сборки не требуется.
- Каноническая запись должна быть стабильной при повторном чтении без
  изменений. Идентификаторы не перенумеровываются ради оформления diff;
  порядок `ChildItems` сохраняется, поскольку имеет семантику.
- Правка Caption или координаты должна менять соответствующее именованное
  свойство. После merge проверяются XSD, ссылки объектной модели, сборка и
  прием платформой. Успешный текстовый merge сам по себе не доказывает
  корректность формы.
- Функции чтения и записи корневого `CustomForm`, общий `FormBase` и
  рекурсивный интерфейс сохранения дочерних объектов теперь установлены
  адресным разбором `frame.so`. Универсальный список именованных свойств
  и методы каждого типа еще требуется связать с этой цепочкой;
  библиотечный цикл чтения, изменения и записи пока не проверен.
  Доказательства: `ev_01f57716ee154fc1a0468946d5c02769`,
  `ev_14a3b7bcee2047a581f2d533f9e28e14`.

Текущее сравнение источников: `ev_d22cf315a7fe47e1a275098e22637b02`.
Фактический охват элементов и проверенные изменения остаются в единой
[матрице](repository-target-state.md#измеряемый-прогресс), границы библиотек
в [карте механизма](platform-mechanism-extraction.md).

## Validation Loop

1. Export a private EPF/ERF with platform tooling into an ignored directory.
2. Decode `Ext/Form.bin` into the object XML package.
3. Rebuild the form stream from object XML.
4. Ask the platform to read or export the rebuilt processor.
5. Compare stable XML and runtime behavior.

For ordinary `Form.bin` writer work, Designer batch export is stricter than a
metadata-only load/check cycle and is the preferred acceptance check.

## Leak Scan Checklist

Before publication or commit, check current content and staged changes for:

- host paths and private mounted volumes;
- `.agent/oacs`, `.oacs`, local databases, key files, and `.env`;
- `nethasp.ini` contents, license server addresses, and license tokens;
- passwords, passphrases, private keys, API tokens, and GitHub tokens;
- EPF/ERF/CF/DT files, platform archives, generated dumps, and customer
  metadata.

Recommended local commands:

```bash
git status -sb
git diff --cached --check
git diff --cached --name-only
git diff --cached | rg -n -i '(/Users/|/home/[^/[:space:]]+|/private/|/var/folders/|password\s*=|passphrase\s*=|secret\s*=|token\s*=|private key|NH_SERVER_ADDR|NH_TCPIP|NHS_SERVER)'
gitleaks detect --source . --redact --no-banner
```

Documentation may mention placeholder values such as
`<local-nethasp.ini>`. Do not record real local values.

## Platform Areas

The platform binary scan has been useful for names and neighboring concepts,
not as a replacement for round-trip validation.

Known useful areas:

- ordinary form designer libraries for control and property vocabulary;
- UI/metadata libraries for shared form concepts;
- core stream/container libraries for `ListInStream` and `ListOutStream`;
- formatting and picture libraries for value serializers.

Keep raw binary strings, symbols, traces, and dumps in ignored local work
directories. Promote only compact verified conclusions into OACS.

## Матрица контролов и границы XML-проверки, 2026-10-03

Сводный реестр всех 25 типов и их следующего эксперимента находится в
[целевом состоянии](repository-target-state.md#измеряемый-прогресс). Имена и
пределы вложенности взяты из `generated_help_catalog.inc` и
`metamodel.cpp`; каталог свойств/событий получен из метаданных справки и
сам по себе не подтверждает сериализацию в Form.bin. Классификация GUID,
ресурсных строк и корреляций с XSD является исследовательским описанием,
не критерием поддержки.

Граф связей: `Form.ChildItems -> Control`; `Panel.ChildItems -> Page или
Control`; `UsualGroup.ChildItems -> Control`. `InputField.DataPath ->
Attributes.Attribute -> TypeDomain` проверен для строкового реквизита.
`CheckBox.DataPath -> Attributes.Attribute -> TypeDomain` подтвержден для
Boolean, включая общий реквизит нескольких флажков. `Button.Click -> событие
Button` закреплено за владельцем элемента. Для прочих связей, событий и
значений требуется независимый платформенный опыт.
Модельный `ChildPolicy` задает только допустимую вложенность модели, не
поведение Designer и не формат записи.

Проверка структуры уже имеет владельца: `form_xml.cpp` строит схемы через
`generate_schemas(Metamodel)` и проверяет XML через libxml2, а
`OrdinaryForm::validate()` проверяет модельные ограничения. Тест
`schema_generator_test` сверяет сохраненные `OrdinaryForm.xsd` и
`OrdinaryFormPalette.xsd` с генерируемыми результатами и содержит проверки
отказа для неверной структуры. Поэтому отдельный вручную поддерживаемый XSD
слой или второй валидатор не нужен без конкретного пропуска в текущем
контракте. Ограничения типа, владельца события, ссылок DataPath и
допустимых сочетаний следует добавлять в существующие дескрипторы/генератор
схемы и graph validator после установления продуктовой семантики.

XSD подтверждает структурное соответствие текущей схеме, но не доказывает,
что Designer создаст такой контрол, что DataPath разрешится в его контекстном
типе или что объект соберется в Form.bin. Например,
необязательный `DataPath` в типе элемента не доказывает платформенный
standalone сценарий. Для связанного CheckBox последующий опыт создания,
сохранения, повторного открытия и строгой выгрузки установил Boolean как
`B` без квалификаторов. Прежнее локальное соответствие `binary` оказалось
ошибочным и удалено. Вариант без DataPath и запись BinaryData остаются
неподтвержденными. Свидетельство: `ev_8f78e081a4f94d268b78bbd956470ad7`.

Текущие исследования и исправления перечислены в журнале под матрицей,
свидетельство сверки: `ev_9e74f3d6108a491bba1207f76ae820fc`.
Для каждого шага фиксировать: контрол и свойство, исходное и измененное
значение в Designer, связанные именованные объекты, результат строгой
выгрузки, изменение кодека, тест отказа для неподдержанного варианта и
результат сборки из XML без исходного Form.bin. Отдельно отмечать
сохранение модуля и владельца события. Если семантика не установлена,
оставлять `UNKNOWN`, не превращать запись потока в публичное свойство.

Три независимых уровня доказательства:

1. XSD: имена, типы значений и структура публичного XML.
2. Объектная модель: владельцы событий, ссылки, категории идентификаторов
   и допустимая вложенность. Один числовой ID может использоваться в разных
   категориях, поэтому общая уникальность всех атрибутов `id` неверна.
3. Бинарный кодек и Designer: сохранение значений, порядок элементов и
   открытие собранной формы. Успех первых двух уровней не заменяет третий.

Проверка матрицы и текущих схем: `ev_dc44c9d1dbbb439cbad4c1978a337add`,
`make test`, 11/11 PASS. Это свидетельство проверяет таблицу и схемы;
результат последующей реализации смешанного порядка приведен ниже.

Пара LabelDecoration.HorizontalAlign: `ev_ffc2f58b1fa7424ab336b33c8f675382`.
Снимки свойств подтверждают Автоматически и Прижать влево; сравнение потоков
показывает изменение только одного свойства и счетчика формы. Второе
отличающееся значение не меняется. Первоначальный снимок повторного открытия
Автоматически был пустым, поэтому прежний отчет не доказывал завершение
опыта. Текущая повторная проверка обоих вариантов устранила этот пробел:
Auto=4 и Left=0 реализованы в именованном кодеке и прошли независимую
сборку XML со строгой выгрузкой. Свидетельства:
`ev_8f78e081a4f94d268b78bbd956470ad7`,
`ev_59e657b3935040b388563d88cfa54fa7`. Смысл второго значения `UNKNOWN`.

### Смешанный порядок, проверенная реализация 2026-10-03

Итоговое свидетельство: `ev_1fe388c655374e298d70a2656226c429`.
Основной кодек читает и пишет верхнеуровневые Button, LabelDecoration и
InputField без прежних ограничений состава. Геометрические ссылки
вычисляются по ID конкретного элемента. Физические записи контролов и
связей выводятся по числовому ID; ChildItems восстанавливаются по
проверенной перестановке порядковых значений геометрии. Повторные и
выходящие за диапазон значения отклоняются; события остаются у владельцев.

## План сравнения одиночных изменений, 2026-09-24

Статус: итерация завершена частично. AC1 PASS: новая сессия Designer повторно
открыла сохраненные EPF с Button; Caption `Launch` и состояние Enabled=false
прочитаны в форме. AC2 PARTIAL: сохранение без изменений дало различие только по
позиционному пути `$/1/10` (3 -> 4); варианты Caption и Enabled изменили ожидаемые
листья и также `$/1/10` (3 -> 5). Роль этой позиции в текущем эксперименте не
подтверждена, различие оставлено видимым. AC3 PARTIAL: строгая выгрузка Designer
успешна для всех четырех EPF, но `oof dump` завершился `OOF1114` для каждого по
пути Button base record `$/1/2/2/1/2/1/0`; именованное свойство не определено и
кодек продуктовой модели не прошел обратную проверку. Отчет находится в
`scan-output/button-property-pilot-actual-diag-20260924T125045Z-23059/report.json`.
Сравниватель показывает только позиционные отличия логического потока формы и
не приписывает им смысл свойств. Пакетный автоматический генератор вариантов
свойств не реализован.
Историческая сверка после пилота: значение Button base record в позиции 17,
отличающее этот вход от канонического, уже записывалось как `2` в `53abed1`.
Техническое имя старого writer `baseStyleState` не доказывает именованное
свойство платформы. Позиция `$/1/10` уже трактуется текущим кодеком как счетчик
сериализации, начиная с `14a49a2`; пилот сам по себе эту семантику не проверял.
Перед следующим экспериментом использовать [разбор повторов](ordinary-form-pattern-audit.md#повторный-разбор-истории-от-2026-09-24).

Целевой охват: 25 типов текущего каталога без внешнего ActiveX.

Критерии исследования перед массовой автоматизацией:

- AC1: один созданный элемент и измененное свойство действительно сохраняются
  в документе формы и читаются после закрытия и повторного открытия.
- AC2: повторное сохранение без правок отделяет служебные изменения от изменения
  исследуемого свойства. Неизвестные различия не скрываются нормализацией.
- AC3: соответствие подтверждается несколькими значениями и обратным изменением,
  затем воспроизводится единственным продуктовым кодеком и строгой выгрузкой Designer.

Последовательность для каждого эксперимента:

1. Зафиксировать версию платформы и синтетическую исходную форму. Создать один
   элемент через механизм, сохраняющий документ формы. Сохранить и открыть заново.
2. Дважды сохранить форму без правок. Зафиксировать различия между этими контрольными
   сохранениями. Идентификаторы и счетчики считать шумом только после проверки их роли.
3. Из одной исходной формы получить независимые варианты, меняя одно свойство.
   Для логического значения проверить оба состояния; для перечисления все допустимые
   значения; для строки пустое значение, ASCII и кириллицу; для числа несколько
   допустимых значений. Отдельно проверить возврат к значению по умолчанию.
4. После каждого сохранения открыть форму заново и прочитать свойство. Сравнить
   внутреннюю структуру потоков, а не абсолютные смещения байтов. Сохранить связь
   с именем элемента, свойством, значением и версией платформы в закрытом отчете.
5. Проверить взаимодействия: второй элемент того же типа, другой родитель,
   страницы, зависимые свойства, события и привязки. Одно свойство может менять
   несколько записей; отсутствие разницы может означать несохраняемое свойство.
6. При неоднозначности исследовать конкретный путь чтения/записи в библиотеке
   нужной версии. Использовать существующие результаты Ghidra и точечные пробы.
7. Перенести подтвержденное правило в именованную объектную модель и дескриптор
   единственного кодека. Собрать форму из XML без исходного бинарного шаблона,
   проверить строгой выгрузкой Designer и чтением измененного значения.

Первый пилот: Button, свойства Caption, Enabled и геометрия. После выполнения
AC1-AC3 повторить на InputField и Table, прежде чем масштабировать перебор.
Прежнее наблюдение OACS о несохранении добавленных во время исполнения элементов
нужно перепроверить на выбранном способе сохранения. Сериализация живого объекта
через `ЗначениеВСтрокуВнутр` сама по себе не доказывает сохранение в `Form.bin`.
