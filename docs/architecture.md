# Архитектура

Проект преобразует обычную форму 1С между бинарным контейнером и именованной объектной моделью. Первая практическая цель - информационное сравнение поддержанных данных формы в Git.

```text
Form.bin -> OrdinaryForm -> Form.xml + Form/Module.bsl + Items/*
Form.xml + Form/Module.bsl + Items/* -> OrdinaryForm -> Form.bin
```

Публичный XML версии 2.1 является редактируемым представлением модели, а не дампом. Он использует собственный словарь обычных форм, включая вложенный `ChildItems`; XML управляемой формы не совместим с ним. `Form.bin` является контейнером для потока формы и модуля. List-stream и bracket-format остаются внутренней деталью кодеков.

## Граница модели

`OrdinaryFormDocument` хранит форму, контролы, страницы, реквизиты, команды, события, типизированные значения, модуль и ссылки на ресурсы. Свойства читаются и меняются через общий API `get_prop_val`, `set_prop_val` и `reset_prop_val` с учетом владельца, типа и известного состояния default.

Читатель может построить неполную именованную проекцию: известные свойства доступны для сравнения, неподдержанные отмечаются диагностикой и `reconstructionComplete=false`. Writer собирает новый файл из доступной модели. Поэтому успешное чтение, сборка или приемка Designer не доказывает сохранение неподдержанных полей исходной формы. Отсутствие diff XML не доказывает отсутствия бинарных различий.

Публичный XML не может включать сырые или индексные данные под другими именами: внутренние потоки, эталонные снимки, записи платформы, бинарные заглушки или скрытые модели. Если значение нужно представить для сборки, оно добавляется как именованное понятие с дескриптором и схемой. Полный контракт и текущие значения перечислены в [ordinary-form-target-contract.md](ordinary-form-target-contract.md).

## Владельцы кода

Пути ниже указаны относительно `sidecars/onec-form-native`.

| Область | Владелец | Назначение |
| --- | --- | --- |
| Объектная модель | `include/oof/model/ordinary_form.hpp`, `src/model/ordinary_form.cpp` | Объекты, свойства, связи и проверка модели |
| Метамодель | `include/oof/model/metamodel.hpp`, `src/model/metamodel.cpp` | Контролы, свойства, события, типы и дескрипторы |
| XML и схема | `include/oof/source`, `src/source` | Разбор XML 2.1, каноническая запись и генерация XSD |
| Кодеки | `include/oof/storage`, `src/storage` | Типизированные значения и внутренние потоки |
| Контейнер | `include/oof/form_bin.hpp`, `src/form_bin.cpp` | Чтение и запись `Form.bin` |
| CLI | `src/cli/main.cpp` | Команды `dump` и `build`, ввод-вывод и диагностика |
| Проверки | `tests`, корневой `CMakeLists.txt` | Проверки модели, XML, потоков и CLI |

Рабочее пространство состоит из существующей C++20 библиотеки `liboof` и CLI `oof`, собранных CMake с libxml2 и zlib. Выполнение `dump` и `build` не загружает библиотеки 1С. Designer применяется отдельно для проверки созданного EPF.

## Общие свойства и расширение

Общие свойства должны иметь общий кодек там, где совпадает их платформенная семантика. Поддержка задается явными возможностями и значениями по умолчанию каждого типа. `Enabled`, `ToolTip`, `Font` и `BorderColor` используют общие механизмы; `LabelDecoration.Font` подключен к общему `FontValue` и проходит собственный строгий цикл. Подтвержденные сведения и ссылки на доказательства: [общие кодеки](research-map.md#общий-кодек-свойств-и-проверенные-исключения-2026-10-05), [контракт Font](ordinary-form-target-contract.md#concept-registry).

При расширении сначала проверьте, может ли существующий владелец обработать новое свойство. Добавляйте именованное свойство и дескриптор, а не новый путь чтения, профиль, файл сопоставлений или сохраненный исходный поток. Не распространяйте общий кодек на тип по сходству названия: проверяйте тип значения, default, применимость и обратный цикл.

Наличие типа в XSD, число типов XML и минимальные положительные примеры не являются оценкой полной поддержки. Текущее покрытие, ограничения и приоритет сравнения описаны в [целевом состоянии](repository-target-state.md), подробные эксперименты - в [карте исследований](research-map.md).

## Контекст конфигурации

Текущий `load_form_bin(bytes, form_name)` получает только контейнер и имя формы. Он не получает метаданные владельца. `decode_attributes` допускает основной реквизит только как локальную ссылку на строку таблицы реквизитов; ссылки на члены объекта также ограничены локальным случаем. Поэтому корректная форма конфигурации может остановиться раньше разбора контролов. Это отдельный недостаток основного пути, который нельзя устранить добавлением свойств очередного контрола.

Целевой путь должен передавать один контекст метаданных в существующий reader и writer. Этот механизм пока не реализован. Контекст содержит:

- владельца формы и его именованный вид;
- соответствия имен метаданных, UUID объектов и `GeneratedType.TypeId`;
- описания стандартных и пользовательских реквизитов, их типов и принадлежности;
- правила разрешения основного реквизита и сегментов `DataPath`.

Индекс строится один раз на выгрузку конфигурации. Разрешение ссылок должно быть общим для всех контролов. Читатель переводит ссылку в именованное понятие модели, а writer восстанавливает платформенную ссылку из этого понятия и контекста. Не следует создавать фиктивный локальный реквизит только для обхода ограничения идентификатора.

У самодостаточной формы контекст может быть пустым. Если форме нужны внешние метаданные, отсутствие или противоречие контекста должно давать явную диагностику. Это один основной путь с проверкой необходимых данных, а не переключение на другой сериализатор.

Чтение контекста не исполняет BSL и не запускает платформу. Оно использует локальную выгрузку с явно заданным корнем, ограничения входного XML и запрет внешних сущностей. Индекс остается локальным состоянием операции; клиентские метаданные не становятся глобальным реестром проекта.

## Семейства записей вместо отдельных форм

Единицей расширения кодека является подтвержденное семейство записей. Контрол собирается из общих компонентов и своих свойств:

```text
контекст конфигурации + контейнер Form.bin
    -> версии компонентов хранения
    -> общая часть контрола + свойства его типа + события + связи
    -> OrdinaryFormDocument
    -> именованный XML

именованный XML + необходимый контекст конфигурации
    -> OrdinaryFormDocument
    -> единый современный writer
    -> новый Form.bin
```

Версии заголовка, owner, страниц, общей части контрола и значений проверяются их собственными кодеками. Связанные ограничения между компонентами сохраняются явно. Совпадение размера записи не является основанием принять неизвестную версию. Описания входных версий остаются внутренними правилами чтения; они не сохраняются в модели, XML или профиле совместимости.

Существующие `decode_common_control_base`, `decode_owner_pages` и кодеки значений являются точками расширения. Уже установленные соответствия свойств должны постепенно использовать общие дескрипторы хранения в том же слое кодеков. Различия применимости, defaults, событий и специальных коллекций остаются у конкретного вида объекта. Замена GUID-ветвления таблицей сама по себе не добавляет поддержку данных.

Расширения формы относятся к владельцу и назначению формы. Их реестр должен описывать GUID, именованный вид расширения, свойства, события и требования к основному реквизиту. Реестр палитры контролов не покрывает этот слой. Общие механизмы событий и значений переиспользуются, но неизвестный GUID нельзя объявить поддержанным только по каталогу, в котором найден файл.

Неизвестное поле требует установления именованного понятия или доказательства, что оно является вычисляемым значением существующего понятия. Различающиеся хвосты записей нельзя объявлять взаимозаменяемыми defaults по сходству соседних полей. В частности, различие добавленных полей общей части старых дочерних контролов остается отдельной непроверенной границей.

## Порядок архитектурного доведения

1. Передать контекст конфигурации в основной путь, разрешить основной реквизит и именованные пути к членам через общий механизм. Сначала проверить один полный случай с локальным реквизитом и один с реквизитом объекта метаданных.
2. Довести реестр расширений формы и их общие свойства и события по семействам владельцев. Нативные проверки выполнять пакетами для новых семейств, а не для каждой формы корпуса.
3. Расширять общие компоненты старых записей и подключать их к уже существующим кодекам контролов. Современный writer сохраняется; работающие обработчики переносятся постепенно, без одновременной замены reader и writer.
4. После изменения общего механизма запускать весь корпус и проверять, какие группы прошли прежнюю границу. Частный анализ нужен для оставшихся различий, а не для каждого экземпляра формы.

Первый архитектурный приемочный пакет должен содержать минимум 12 контролов, локальные реквизиты и ссылки на члены объектов конфигурации. Один механизм разрешения должен обслужить все эти связи. После изменения именованного свойства XML собирается без исходного потока, конфигурация применяется, результат строго выгружается из той же базы и сравнивается по именованной модели. Отсутствующий контекст, неизвестный внешний тип и неверный член должны давать определенную диагностику. Существующие проверки самостоятельных форм обязаны продолжать проходить.

## Раздельные показатели готовности

Нужно различать классификацию дескрипторов, поддержку версий хранения, разрешение метаданных, полноту восстановления конкретной формы и нативную проверку результата. `descriptorCoverageComplete` относится только к классификации дескрипторов.

Корпусный отчет показывает первую ошибку формы. Нераспознанное расширение может скрывать как работающие кодеки контролов, так и следующие ошибки. Поэтому число полных форм не является процентом готовности всех кодеков, а устранение первой ошибки не доказывает полного восстановления формы. Состояния полного восстановления, частичной проекции и ошибки должны учитываться отдельно.
