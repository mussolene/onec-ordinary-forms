# Архитектура

Продукт: библиотека C++20 `liboof` и CLI `oof`, которые преобразуют обычную
форму 1С в самостоятельный редактируемый пакет. Платформа не нужна для
исполнения CLI. Она нужна как независимый эталон приемки форматов.

```text
Form.bin -> контейнер -> поток формы -> OrdinaryFormDocument
                                      <-> Form.xml + Module.bsl + Items/*
Form.bin <- контейнер <- поток формы <- OrdinaryFormDocument
```

Текущая проверочная платформа: 8.5.1.1343 Linux, без ActiveXControl.
Writer преимущественно пишет современные поколения, в том числе корень 27
и FormBase 18. Поддержка старого входа не означает запись исходной версии
или совместимость результата с 8.2. Точный контракт версий находится в
[контракте модели](ordinary-form-target-contract.md#версии).

## Что уже устроено правильно

- Одна именованная модель между BIN и XML, без обязательного исходного BIN.
- Типизированные значения, ссылки на объекты, события и вложенные элементы.
- Общие кодеки цвета, шрифта, рамки, типов, привязок и других значений.
- Отдельные метаданные конфигурации для необязательного разрешения имен.
- Отказ при неполной модели, чтобы не выпускать форму с потерянными данными.

Эту границу сохраняем. Новый бинарный движок, перенос платформенных библиотек
в продукт или скрытый исходный поток не устраняют недостающие именованные
понятия модели.

## Где реализация отстает от этой архитектуры

`StorageCodec` в метамодели задает категорию хранения, например `control_info`.
Он не содержит доказательства всех поколений и состояний этой категории.
В `form_stream.cpp` известные поля читаются общими кодеками, но оставшаяся
часть ряда записей сравнивается с каноническим образцом. Поэтому контрол
присутствует в модели и XSD, а конкретная форма с ним все еще отвергается
либо получает `reconstruction_complete=false`.

Целая форма требует совместной поддержки корня, расширения, меню, команд,
источников таблиц, колонок, редакторов и значений. Неподдержанная коллекция
меню блокирует форму с десятками уже поддержанных простых контролов.
Декодер сообщает первый отказ, поэтому устранение одного отказа может
только открыть следующий. Числа и доказательства: [текущий статус](repository-target-state.md).

Единица дальнейшей реализации: **семейство сохраняемых объектов вместе с
чтением, именованной моделью, записью и нативной приемкой**. Список свойств
контрола остается справочником применимости. Подробный диагноз:
[аудит](ordinary-form-pattern-audit.md).

## Владельцы кода

Пути относительно `sidecars/onec-form-native`:

| Слой | Владелец | Обязанность |
| --- | --- | --- |
| Объектный граф | `include/oof/model/ordinary_form.hpp`, `src/model/ordinary_form.cpp` | Свойства, значения по умолчанию, коллекции, связи, проверка инвариантов |
| Дескрипторы | `include/oof/model/metamodel.hpp`, `src/model/metamodel.cpp` | Имена, типы, применимость, доступ, сохраняемость, категории кодеков |
| Публичные исходники | `src/source/form_xml.cpp`, `src/source/schema_generator.cpp` | XML 2.1, каноническая запись, генерация схем |
| Типы конфигурации | `src/source/metadata_xml.cpp`, `include/oof/metadata_context.hpp` | Необязательное разрешение имен и проверка ссылок |
| Формат хранения | `src/storage/form_stream.cpp`, `src/storage/value_codec.cpp` | Общие значения, поколения записей, сборка потока из модели |
| Контейнер | `src/form_bin.cpp`, `include/oof/storage/form_bin_container.hpp` | Потоки формы и модуля внутри Form.bin |
| Файловый пакет | `src/cli/main.cpp` | Команды, диагностика, модуль, ресурсы, безопасная запись |
| Проверки | `tests`, `CMakeLists.txt` | Модель, XML/XSD, кодеки, контейнер, CLI |

Перемещение большого `form_stream.cpp` по новым файлам само по себе не
увеличит поддержку. Сначала завершаем общий механизм в существующем
владельце. Выделение кода допустимо при ясной границе и законченной паре
reader/writer, без второго маршрута для прежних частных случаев.

## Конфигурация и форма

Стандартные типы платформы обрабатывает продукт. Прикладной тип конфигурации
хранит свою UUID и необязательное имя. Идентичность типа, идентичность
реквизита и идентичность объекта формы различаются.

`--metadata` и `--type-schema` могут обогатить имена и проверить связи.
Собранный пакет содержит необходимые идентичности; writer не должен
восстанавливать их из исходной базы. XSD конфигурации описывает декларации
типов, но не грамматику Form.bin. Категории GeneratedType Ref/List также
не задают токены бинарной сериализации.

## Как завершаем общий механизм

1. Группируем текущие отказы по одному владельцу и поколению записи.
2. Устанавливаем недостающее понятие по существующим SO/DLL и независимому
   примеру Designer. Уже доказанные Color, Font и другие значения используем
   повторно.
3. Добавляем понятие в модель, дескрипторы и XML/XSD; замыкаем чтение и запись.
4. Проверяем изменения на целом самостоятельном пакете и одном нативном
   наборе минимум с десятью применимыми контролами.
5. После завершения семейства измеряем прирост полных форм корпуса, переходы
   между категориями и регрессии. Снятый первый отказ учитываем отдельно.

Неподдержанное поле нельзя молча отбросить. Лишнюю проверку можно убрать,
когда существующий типизированный кодек или нативный контрпример доказывает,
что она неверна. Карта работ и источников: [реализация](platform-mechanism-extraction.md#implementation-map).
